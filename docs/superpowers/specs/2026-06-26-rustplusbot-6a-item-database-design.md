# Subsystem 6a — Item Database, Core Calculators & Refresh Tool

**Date:** 2026-06-26
**Branch:** `feat/item-database` off `develop`
**Status:** Design approved, ready for implementation plan
**Predecessor:** 4c Smart Storage Monitors (PR #27, merged `d2d57a1`, head of `develop`)

---

## 1. Summary

Subsystem 6 is the **item database & calculators**: a bundled, versioned, offline Rust item
dataset plus the commands that read it (`/craft /decay /recycle /research /upkeep /item`, in-game
equivalents). This is the **6a slice** — the data foundation plus the four most-used calculators —
and, critically, a **refresh tool** so the dataset never silently rots.

6a delivers three things:

1. **A versioned, embedded item dataset + `IItemDatabase` seam** — our own typed schema (the
   "proto"), stamped with a `SchemaVersion` and per-section `sourceDate` provenance. The single
   source of truth for item data, superseding 4c's name-only `IItemNameResolver`.
2. **A generator CLI tool** (`tools/RustPlusBot.ItemData.Generator`, a dev/maintainer console
   project, NOT shipped in the bot) that pulls names from a maintained current feed, scrapes
   recycle/craft/research from rustlabs/wiki.rustclash.com into our schema, **validates strictly
   and fails loudly on shape drift**, and emits the embedded resource. Re-runnable on every Rust
   update — the answer to "this third-party data can be outdated."
3. **Four calculators**, each exposed both as an ephemeral Discord slash command and an in-game
   `!command`: `/item` `/recycle` `/craft` `/research` (+ `!item !recycle !craft !research`).

### Why a refresh tool (the motivating problem)

The reference bot (rustplusplus) bundles static JSON for these calculators. Investigation showed
two very different freshness profiles:

- **Names/ids (`items.json`)** — updated **2026-04-08**, current. Generated by `process_items.js`
  from a maintained feed.
- **Calc data (`rustlabs*.json`: recycle/craft/research/stack/despawn)** — **frozen since
  2024-09-07** (~20 months stale at time of writing). Generated by `process_rustlabs.js`, which
  **HTML-scrapes `wiki.rustclash.com` with brittle regex** (and is GPL-3.0).

Bundling that frozen calc data as-is would ship knowingly-wrong recycle yields and recipes after
20 months of Rust updates. So 6a does NOT copy frozen files: it defines our own schema and ships a
tool that regenerates a fresh-as-of-run snapshot, with validation that screams when the upstream
page shape changes instead of silently emitting garbage.

## 2. Scope

### In scope (6a)

- New project `RustPlusBot.Features.ItemData` (pure data/calc leaf): the dataset schema, embedded
  resource, `IItemDatabase` + `EmbeddedItemDatabase`, the pure `ItemLookup`.
- New dev tool `tools/RustPlusBot.ItemData.Generator` (console; not referenced by the bot).
- Four calculators, each slash (ephemeral embed) **and** in-game (terse line), in the existing
  `Features.Commands` project:
  - `/item` · `!item` — display name, id, stack size, despawn time
  - `/recycle` · `!recycle` — recycler yield
  - `/craft` · `!craft` — ingredients + craft time
  - `/research` · `!research` — scrap cost
- Shared pure `ItemLookup` (name-or-id resolution with disambiguation).
- Re-point 4c's `IItemNameResolver` at `IItemDatabase`; remove StorageMonitors' private
  `items.json`. One source of truth.
- EN/FR localized replies for all four commands and the three lookup outcomes.

### Deferred (6b+)

- `/decay`, `/upkeep`, `/durability` (the durability source is ~19 MB — never bundle raw),
  `/smelting`, `/cctv`.
- Recycle yield variants beyond the recycler (safe-zone recycler, shredder).
- Live-scrape cadence automation / scheduled refresh (6a's tool is run manually).
- Discord slash-command autocomplete for the item argument (6a uses typed free-text).
- 4c's storage-monitor recycle/upkeep calc — **now unblocked** by this dataset, but a separate
  slice.

### Explicit non-goals

- **No** new entities, migrations, events, options, or background services. This is read-only
  static data; nothing touches the database schema or the live socket.

### 3.2 Dependency direction

`ItemData` is a **leaf**: it references only `Abstractions` + `Localization`. `Features.Commands`
and `Features.StorageMonitors` reference `ItemData` (one new edge each). Nothing references back
into a feature, so no cycle is possible (this avoids the 3c circular-dependency trap where
`Connections → Workspace` was mis-assumed). The generator tool references `ItemData` for the
schema records but is **not** referenced by the bot.

### 3.3 The dataset schema (the "proto")

One embedded JSON resource (`item-data.json`) deserialized into immutable records:

```
ItemDataset(
    int SchemaVersion,                       // bump when the shape changes; loader rejects mismatch
    DatasetSources Sources,
    IReadOnlyList<ItemRecord> Items)

DatasetSources(
    DateOnly NamesAsOf, DateOnly RecycleAsOf, DateOnly CraftAsOf, DateOnly ResearchAsOf)

ItemRecord(
    int Id, string Name, int StackSize, int? DespawnSeconds,
    RecycleYield? Recycle, CraftRecipe? Craft, ResearchCost? Research)   // null = N/A for that item

RecycleYield(IReadOnlyList<YieldEntry> Recycler)            // 6a: recycler only
YieldEntry(int ItemId, int Quantity, double Probability)
CraftRecipe(IReadOnlyList<Ingredient> Ingredients, double TimeSeconds, int? WorkbenchLevel)
Ingredient(int ItemId, int Quantity)
ResearchCost(int Scrap)
```

- **One record per item**, all calculator data inlined — no runtime cross-file joins.
- **Provenance is first-class** (`DatasetSources`) so every command footers "data as of `<date>`".
- **`SchemaVersion`** is the proto version; the loader rejects a mismatched bundle loudly.

### 3.4 The seam

```
public interface IItemDatabase
{
    DatasetSources Sources { get; }       // for "data as of" footers
    ItemRecord? GetById(int id);
    ItemMatch Resolve(string query);      // name-or-id → ItemLookup result
}
```

`EmbeddedItemDatabase` is a singleton: loads the resource once into a
`FrozenDictionary<int, ItemRecord>` plus a lowercased-name index (same pattern as 4c's
`EmbeddedItemNameResolver`). 4c's `IItemNameResolver.Resolve(id)` becomes a one-line adapter:
`_db.GetById(id)?.Name ?? "Item " + id`.

### 3.5 `ItemLookup` (name→item resolution)

Pure, dependency-free, exhaustively unit-tested. Result:

```
ItemMatch = Found(ItemRecord) | Ambiguous(IReadOnlyList<ItemRecord> Candidates) | NotFound
```

Algorithm (deterministic, ordered):

1. **Numeric input** → if it parses as int and `GetById` hits, `Found`. A numeric MISS falls
   through to name matching (item names can contain digits), not straight to `NotFound`.
2. **Exact name match** (case-insensitive, trimmed) → `Found`. Exact always beats any substring.
3. **Substring matches** (case-insensitive `Contains`): 1 → `Found`; 2..N → `Ambiguous(top-N)`;
   0 → `NotFound`.
   - Ranking for `Ambiguous`: prefix-matches first, then shorter names, then alphabetical
     (deterministic tie-break so tests are stable).
   - N cap = top 10.
4. Empty/whitespace query → `NotFound` (with a usage hint at the call site).

## 4. Command surfaces

All command plumbing stays in `Features.Commands` (already owns the dispatcher, `ICommandHandler`,
slash modules, `/help` catalog). It gains one project ref: `ItemData`.

### 4.1 In-game `!commands`

Four `internal sealed ICommandHandler` in `Features.Commands/Handlers/`, registered `AddScoped`
in `AddCommands` (registration-count test 12→16). Each takes `CommandContext` (carries the arg
string + `Culture`), calls `IItemDatabase.Resolve(arg)`, switches on `ItemMatch`, and returns a
**terse one-line** localized reply via `ILocalizer`. Static data only — **no socket / no live
server required** (works while disconnected, unlike `!pop`/`!time`). Pure formatters
(`ItemLine`/`RecycleLine`/`CraftLine`/`ResearchLine`) in `Features.Commands/Formatting/`.

Example: `!recycle ak` → `AK-47 → Scrap ×?, Metal Fragments ×?`

### 4.2 Slash commands

One `public ItemCommandModule : InteractionModuleBase<SocketInteractionContext>` in
`Features.Commands/Modules/` (the proven 3c shape: inject `IServiceScopeFactory`, resolve
per-interaction, respond **ephemeral**), discovered via the already-registered
`InteractionModuleAssembly`. Each `[SlashCommand]` has a required `string item` parameter (typed
free-text; autocomplete deferred). Resolves culture via `IWorkspaceStore.GetCultureAsync`, calls
the same `IItemDatabase` + same formatters, renders a **rich ephemeral embed** with a "data as of
`<date>`" footer from `Sources`.

### 4.3 Outcome rendering (consistent across both surfaces)

- `Found` → the calculator's normal output.
- `Ambiguous` → "Did you mean: AK-47, Semi-Auto Rifle, …?" (candidate names, capped). In-game =
  one line; slash = ephemeral text.
- `NotFound` → "No item matching '`<query>`'." (localized EN/FR).

### 4.4 `/help`

The 3c `CommandHelpCatalog` gains the four new commands so they appear in `/help` (its golden-list

- count tripwire guards drift).

## 5. The generator tool

`tools/RustPlusBot.ItemData.Generator` (console, .NET, not shipped in the bot). Two source
adapters behind interfaces so the parse/validate logic is testable offline:

- **`INamesSource`** → names/ids/stack from the maintained current items feed (the
  well-maintained, currently-fresh source).
- **`IRustLabsSource`** → recycle/craft/research. Default implementation scrapes
  rustlabs/wiki.rustclash.com (HTML → our schema). An `--offline` ingest-existing-JSON
  implementation exists for transforming a known snapshot without network.

**Validation (`DatasetValidator`) — fail loudly, never ship garbage:**

- expected item count within a tolerance band (catch a page that returned an error shell),
- every yield/ingredient/recipe id resolves to a known item name,
- non-empty recycle/craft/research tables where the upstream says they should exist,
- on any failure: non-zero exit + a message naming the drifted section; does **NOT** overwrite the
  existing good embedded bundle.

**Output:** writes `item-data.json` (our schema) + stamps `SchemaVersion` and per-section
`sourceDate`. Re-run on each Rust update to refresh.

The live scrape itself is the one untested-by-design integration shim (isolated behind
`IRustLabsSource`). The transform + validation are fully unit-tested against known-good and
deliberately-drifted fixtures.

## 6. Error handling

- **Embedded load failure** (missing/corrupt resource, `SchemaVersion` mismatch) → throw at
  singleton construction = fail-fast at startup (consistent with the bot's `ValidateOnStart`
  gates). A malformed dataset never boots silently.
- **Duplicate parsed ids** → last-wins group before freezing (the 4c `EmbeddedItemNameResolver`
  fix; two string keys parsing to the same int must not hard-fault `ToFrozenDictionary`).
- **Calculator on an item lacking that data** (`Recycle`/`Craft`/`Research` null) → localized
  "not recyclable / not craftable / no research cost" reply, never a null-ref.
- **Empty/whitespace arg** → `NotFound` path with a usage hint.
- **Generator validation failure** → non-zero exit, names the drifted section, leaves the good
  bundle intact.

## 7. Testing

- **`ItemLookup`** — exhaustive `[Theory]`: exact-wins-substring, prefix ranking, `"ak"` case,
  numeric hit/miss/fallthrough, empty, whitespace, ambiguous cap, deterministic tie-break.
- **`EmbeddedItemDatabase`** — loads the real bundle, count sanity, duplicate-id degrade,
  known-item spot-checks, `Sources` populated, `SchemaVersion`-mismatch throws.
- **Formatters** — Found/Ambiguous/NotFound × EN/FR.
- **The four `ICommandHandler`s** — via the existing handler test harness (xUnit `Assert`, NOT
  FluentAssertions — repo convention).
- **Generator validation** — unit-tested against a known-good fixture AND a deliberately-drifted
  fixture (proves it fails loudly). Live scrape isolated behind `IRustLabsSource`, untested by
  design.
- **Full suite `-maxcpucount:1`, read per-assembly counts** — a fake missing a new `IItemDatabase`
  member silently drops a whole assembly's tests. Any harness resolving `IItemDatabase` needs a
  fake/registration.

## 10. Decisions locked in brainstorming

- **Scope**: core 4 (`/item /recycle /craft /research`) + the dataset foundation + the refresh
  tool. Decay/upkeep/durability/smelting/cctv deferred to 6b.
- **Seam strategy**: new shared `ItemData` project owns the full `IItemDatabase`; 4c's
  `IItemNameResolver` becomes a thin adapter; old private `items.json` removed. One source of
  truth.
- **Data source**: reuse rustplusplus's data origins (current names feed + rustlabs scrape), but
  through OUR typed, validated, versioned schema — not by copying frozen files.
- **Refresh**: our own schema (the "proto") + a `tools/` generator CLI that regenerates a fresh
  snapshot, validates strictly, and fails loudly on shape drift. Run manually on each Rust update.
- **Tool sources**: names from the maintained current feed; recycle/craft/research scraped fresh,
  schema-validated; per-section `sourceDate` stamps.
- **Surfaces**: both slash (ephemeral embeds) and in-game (terse lines), full parity.
- **Surface home**: surfaces in `Features.Commands`; data + calculators + lookup in `ItemData`
  (a pure leaf).
- **Lookup**: case-insensitive, exact-wins-then-substring, single→use, multiple→"did you mean"
  top-10, zero→not-found, numeric→direct id (with fallthrough on numeric miss).
